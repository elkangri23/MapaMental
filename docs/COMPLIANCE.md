**Auditoría de código, seguridad e interfaz (2026-11-16):** build completo con Node 24.22.2 correcto; `npm audit --omit=dev` reportó cero vulnerabilidades. En Chrome temporal aislado, Lighthouse dio 100/100 en accesibilidad móvil y escritorio, con 35 auditorías disponibles aprobadas y cero fallidas tanto en el mapa como en una diapositiva con recorrido, formulario ficticio y tabla. Reflujo sin desbordamiento horizontal a 320 y 640 CSS px; diálogo móvil con scroll interno. No equivale a conformidad WCAG: no se usó lector de pantalla, faltan estados/criterios por revisar y no se ejecutó pentest. Ver [`reviews/2026-11-15-code-audit.md`](reviews/2026-11-15-code-audit.md), [`reviews/2026-11-15-security-audit.md`](reviews/2026-11-15-security-audit.md) y [`VERIFICATION.md`](VERIFICATION.md).

Esta matriz usa [OWASP Top 10:2025](https://owasp.org/Top10/2025/) y [WCAG 2.0](https://www.w3.org/TR/WCAG20/). La app es de uso personal y local, pero recibe contenido de archivos y proveedores LLM; por eso se mantienen controles de validación y aislamiento. WCAG 2.0 AA solo puede declararse cuando se revisen los criterios A y AA aplicables en todas las páginas y estados.

### Actualización de SSRF — 2026-11-16

La validación IPv6 se endureció para rechazar `2001::/23` y `3fff::/20` comparando numéricamente los dos primeros hextetos. Esto cubre formas que el parser WHATWG normaliza, como `2001:0::1` → `2001::1`, y el rango de documentación IPv6. IANA clasifica ambos como bloques especiales no globalmente alcanzables; la política del producto bloquea esos prefijos enteros para destinos de proveedores. Fuente: [Registro IANA de direcciones IPv6 de propósito especial](https://www.iana.org/assignments/iana-ipv6-special-registry). Se comprobaron nueve direcciones bloqueadas y tres direcciones de límite/públicas permitidas. Build y `npm audit --omit=dev` pasaron con Node 24.22.2. Esto no completa la auditoría SSRF/TLS ni el análisis formal de amenazas.

## Comprobaciones realizadas en este cambio

- 2026-11-16: `npm run build` correcto con Node 24.22.2 y `npm audit --omit=dev` reportó cero vulnerabilidades. Chromium en producción temporal aislada; Lighthouse snapshot móvil/escritorio 100/100 Accessibility (35 auditorías disponibles, 0 fallidas) en mapa y editor de diapositiva con bloques.
- La inspección de texto sobre fondo efectivo encontró contraste insuficiente en etiquetas y ordinal de diapositiva, texto de formulario ficticio, fuente de mapa y marcadores de recorrido. Se corrigieron en CSS. Lighthouse en la diapositiva detectó además dos botones cuyo texto visible «Orden» no coincidía con su nombre accesible; se cambió a «Mover antes/después», tras lo que móvil/escritorio pasaron sin fallos. También se localizaron instrucciones y controles React Flow, se nombró el landmark de chat y se añadieron anuncios de conversación/guardado.
- Teclado observado: Tab enfoca skip link; Enter enfoca `<main>`; foco entra en proveedores, circula con Tab, Escape cierra y restituye el foco; F2 enfoca el campo de nombre de la idea. La vista de lista permite seleccionar una idea con Enter.
- Emulación 320 CSS px: documento sin scroll horizontal y controles visibles; diálogo de proveedor cabe en ancho y alto con scroll interno. Emulación 640 CSS px (aproximación a zoom 200 % desde 1280): sin scroll horizontal ni controles fuera de pantalla.
- 2026-11-16: instancia de producción en loopback con carpetas de datos temporales. Las 19 operaciones API protegidas de proyectos, proveedores y propuestas/aplicación/deshacer IA devolvieron 403 sin cookie y cabeceras de origen esperadas; con sesión válida, `GET /api/projects` devolvió 200. Origen ajeno y `Host: localhost` devolvieron 403; reutilizar el nonce devolvió 401. La cookie mostró `HttpOnly`, `SameSite=Strict`, `Path=/api` y caducidad de 12 h. `/` devolvió CSP de producción, `X-Frame-Options: DENY` y `X-Content-Type-Options: nosniff`. Cuerpo de 8 MiB + 1 byte: el servidor registró respuesta 413. No se creó proyecto ni se contactó a un proveedor.
- Los colores del mapa/canvas y la diapositiva se inspeccionaron en DOM; el escaneo automático ignora fondos de gradiente, pseudo-elementos y estados no abiertos, por lo que no sustituye el examen completo. No se usó lector de pantalla real ni se declara conformidad WCAG.

- `npm run build` completado correctamente en Node 24.22.2 en cada iteración final.
- La CSP y cabeceras de seguridad se comprobaron por HTTP en el servidor de producción compilado, para `/` y `/api/health`; página, JS y CSS respondieron correctamente. Recorrido temporal aislado en puerto 43932 y carpetas temporales; no se usaron proyectos personales ni proveedor LLM.
- Validación de URL del proveedor comprobada directamente: se rechazaron IPv4 privadas, IPv6 unique-local/link-local/documentación y un dominio que resolvía a loopback; se aceptaron loopback local y `api.openai.com`. Se resuelven las direcciones y se bloquea el host si alguna es local/privada. Se usa un socket con DNS fijado a la lista previamente revisada; falta probarlo con perfil local/remoto en Windows. No se conectó a un proveedor funcional.
- Handshake de producción: el estado sin cookie devuelve 204; el nonce de un uso se canjea y la UI carga lista, configuración y proyecto temporal (200/201). El estado con cookie devuelve 200; no genera error de consola.
- Navegación por teclado: el skip link recibe foco; el diálogo de proveedores recibe foco inicial, cierra con Escape y devuelve foco al botón que lo abrió. La vista textual del mapa presenta ideas y permite seleccionar nodos. Se emuló 375×812 con movimiento reducido y `documentElement.scrollWidth === innerWidth`.
- Lighthouse móvil y desktop sobre producción: Accessibility, Best Practices, SEO y Agentic Browsing 100; las 50 auditorías disponibles pasaron en ambas vistas. En móvil (375×812) no hubo desbordamiento horizontal, campos sin nombre ni errores de consola.

Lighthouse no equivale a conformidad WCAG 2.0 AA. La comprobación estática no sustituye un recorrido de red y TLS con el paquete/distribución final.

### Seguimiento OWASP — 2026-11-17

En T-015 se verificaron 32 direcciones representativas de los registros IANA (25 especiales rechazadas, cinco públicas y dos loopback locales aceptadas), el rechazo de redirecciones sin solicitar su destino y el rechazo de `127.0.0.1.nip.io` al resolver a loopback, con cero sockets al canario. Se corrigió el rechazo estático de `localhost.`, `.local.` e `.internal.`. La conexión HTTPS fija explícitamente el SNI al hostname configurado y exige validar el certificado; un servidor HTTPS local con certificado de CA de prueba completó la consulta y observó SNI `localhost`. Se añadió y verificó un máximo de tres generaciones IA simultáneas (la cuarta se rechaza con 429 antes de contactar al proveedor). Una simulación determinista de las funciones de resolución SSRF y lookup del socket confirmó la IP fijada frente al cambio DNS, pero no alcanzó una petición HTTP ni abrió conexión. También faltan permisos/errores de disco y análisis formal de amenazas. El alcance sigue siendo una revisión parcial, no una certificación.
